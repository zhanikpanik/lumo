# UX / Product Decision Log

Живой документ для фиксации неочевидных UX/дизайн/продуктовых решений.

Цель:

- не терять контекст "почему так сделано";
- быстро проверять договорённости перед доработками;
- складывать сюда как уже принятые решения, так и вопросы "на уточнение".

## Как пользоваться

Для каждого пункта фиксируем:

- **Статус:** `decided` / `pending`
- **Контекст:** какая боль/сценарий
- **Решение:** что именно делаем
- **Последствия:** на что влияет в UI/логике

## Решения (decided)

### 1) Marketplace заказы (Glovo / Yandex) в POS

- **Статус:** decided
- **Контекст:** куда должны попадать заказы маркетплейсов в интерфейсе.
- **Решение:** входящие заказы создаются как обычные POS-заказы в `orders` с `order_source = 'glovo' | 'yandex_eda'`; отображаются в общем `OrdersScreen`.
- **Последствия:** единая операционная лента заказов, без отдельного "второго экрана" под маркетплейсы.

### 2) Что делать с "чеком" маркетплейса

- **Статус:** decided
- **Контекст:** как отражать оплату в POS, если деньги идут через агрегатора.
- **Решение:** для auto-paid marketplace заказов создаётся `payments` запись с `method='other'` и idempotency ключом провайдера (`glovo:<id>`, `yandex_eda:<id>` для CARD).
- **Последствия:** заказ участвует в сменной выручке и отчётах, но не увеличивает кассовую наличность как обычный `cash`.

### 3) Поведение CASH vs CARD у Yandex Eda

- **Статус:** decided
- **Контекст:** для CASH нельзя ждать ручной оплаты, кухне нужно готовить сразу.
- **Решение:**  
  - `CARD`: заказ сразу `paid`, списание через `pos_finalize_order_stock`;  
  - `CASH`: заказ `active`, списание через `pos_finalize_marketplace_active_stock`, отмена через `pos_cancel_unpaid_marketplace_order`.
- **Последствия:** кухня начинает работу сразу, а кассовый сценарий остаётся корректным.

### 4) Уведомления по marketplace заказам

- **Статус:** decided
- **Контекст:** новые заказы должны быть заметны одинаково для Glovo и Yandex.
- **Решение:** при новом marketplace заказе: звук + пульсация карточки + счётчик на lock screen (`Новых заказов: N`) до открытия заказа.
- **Последствия:** единое поведение для всех каналов, меньше пропущенных заказов.

### 5) Takeaway режим: список вместо зала

- **Статус:** decided
- **Контекст:** для точки "на вынос" нет смысла в плане столов.
- **Решение:** при `venue_type='takeaway'` основной режим — список заказов, таб "Столы" скрыт.
- **Последствия:** упрощённый поток работы, меньше лишней навигации.

### 6) Фильтры OrdersScreen

- **Статус:** decided
- **Контекст:** dropdown с 2-3 опциями перегружает UI.
- **Решение:** статусные фильтры переведены на `SegmentedSwitcher`; в takeaway скрыта сортировка, если доступна только одна опция.
- **Последствия:** меньше кликов, более быстрый выбор состояния.

## Вопросы на уточнение (pending)

### A) Фильтр "Мои / Все" по официанту

- **Статус:** pending
- **Контекст:** официанту нужен быстрый фокус на своих заказах, но иногда нужен общий обзор.
- **Вариант решения:** для роли `waiter` показать switcher `Мои | Все`; для `cashier/manager/owner` оставить общий список + поиск/доп. фильтр при необходимости.

### B) Стоит ли оставлять сортировку "По столам" в списке

- **Статус:** pending
- **Контекст:** часть сценариев уже закрывается вкладкой "Столы".
- **Вариант решения:** либо убрать сортировку по столам, либо оставить только для restaurant как быстрый инструмент без перехода в floor plan.
