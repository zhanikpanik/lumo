# Интеграция приложения сотрудников с Lumo

## Цель

Подключить приложение сотрудников для работы с закупочными листами и поставками к существующему Lumo без отдельной базы, копии схемы или второй реализации складской логики.

Приложение сотрудников, админка и дашборд должны видеть одни документы и использовать один серверный процесс проведения поставки.

## Принятые решения

- Приложение работает на личных телефонах сотрудников.
- Приложение и админка требуют подключение к сети; полноценный offline-first режим не нужен.
- InstantDB используется для реактивного чтения данных.
- Все складские записи выполняются через activation worker.
- В приложении сотрудников и полной форме админки можно добавлять ингредиенты при приёмке.
- На дашборде доступна только быстрая приёмка: принять как есть или изменить фактическое количество существующих строк.
- Закупленное и фактически принятое количество должны храниться раздельно.
- Все поверхности используют одну серверную команду приёмки.

## Размещение в monorepo

Рекомендуемое расположение:

```text
apps/
├── activation-worker
├── admin
├── pos
└── staff
```

`pnpm-workspace.yaml` уже включает `apps/*`, поэтому приложение следует подключить как workspace-пакет:

```json
{
  "name": "@lumo/staff",
  "private": true,
  "dependencies": {
    "@lumo/data": "workspace:*",
    "@instantdb/react-native": "^1.0.52"
  }
}
```

Если приложение не React Native, вместо `@instantdb/react-native` используется `@instantdb/react`.

## Единый источник данных

Приложение MUST использовать ту же InstantDB-среду, что POS и админка.

```env
EXPO_PUBLIC_INSTANT_ENV=development
EXPO_PUBLIC_INSTANT_APP_ID=<development InstantDB app ID>
EXPO_PUBLIC_ACTIVATION_WORKER_URL=<activation worker URL>
```

Для production используются соответствующие production-значения.

Схема и доменные типы импортируются из `@lumo/data`:

```ts
import type { AppSchema } from '@lumo/data';
```

Приложение MUST NOT:

- создавать собственную копию `instant.schema.ts`;
- хранить отдельные копии поставок;
- напрямую менять `deliveryDocuments`, `deliveryLines`, `stockItems` или `inventoryMovements`;
- использовать Instant Admin Token;
- вызывать admin warehouse endpoint от имени сотрудника.

## Текущее состояние Lumo

### Уже существует

- `packages/data/src/instant.schema.ts` — общая InstantDB-схема;
- `packages/data/src/warehouseQueries.ts` — запросы склада и поставок;
- `apps/activation-worker/src/warehouse-command-runner.mjs` — серверные складские команды;
- `apps/activation-worker/src/instant-command-runner.mjs` — идемпотентность и resource claims;
- `POST /v1/admin/warehouse-commands` — endpoint для owner/manager;
- `create-delivery`, `update-delivery`, `receive-delivery`, `cancel-delivery`, `restore-delivery`;
- атомарное проведение поставки и обновление складских остатков;
- защита от повторного выполнения через `operationId`;
- проверка конкурентных изменений через `version` и `commandClaims`.

### Пока отсутствует

- связь Instant-пользователя с `employee`;
- отдельная авторизация складских команд сотрудников;
- `POST /v1/staff/warehouse-commands`;
- отдельное procurement-право сотрудника;
- разделение заказанного и фактически принятого количества;
- атомарная приёмка с передачей скорректированных строк;
- серверная команда отправки закупочного листа поставщику;
- полная модель частичной приёмки, если она потребуется.

Приложение не должно обходить эти пробелы прямыми клиентскими транзакциями.

## Авторизация сотрудников

Поскольку приложение используется на личных телефонах, каждый сотрудник входит как отдельный Instant-пользователь.

Рекомендуемый поток:

1. Сотрудник вводит email.
2. InstantDB отправляет magic code.
3. После входа приложение получает authenticated `$user`.
4. `$user` связан с активным `employee`.
5. `employee` связан с заведением и имеет procurement-право.
6. Worker определяет сотрудника по bearer token, а не доверяет `employeeId` из тела запроса.

Целевая связь в схеме:

```text
$user ← employeeAuthUser → employee → venue
```

Связь `$user → employee` должна быть явной. Сопоставление только по email не является достаточным постоянным идентификатором.

### Procurement-права

Не следует выводить доступ к закупкам только из ролей `waiter` или `cashier`. Нужна отдельная capability:

```text
purchasingRole:
- requester — создаёт, редактирует и отправляет закупочные листы;
- receiver — дополнительно принимает поставки;
- manager — полный доступ, включая отмену и восстановление.
```

Worker всегда проверяет:

- пользователь аутентифицирован;
- существует связанный `employee`;
- `employee.status === "active"`;
- employee принадлежит указанному venue;
- procurement-роль разрешает конкретную команду.

## Permission rules

Текущий helper `venueMembers` включает owner, manager и активированные POS-устройства. Нельзя просто добавить сотрудников приложения в этот широкий helper: это может открыть им заказы, кассу и финансовые данные.

Следует создать отдельное правило для procurement-чтения и применить его только к нужным сущностям:

- ингредиенты, необходимые для закупки;
- склады;
- закупочные листы и их строки;
- поставки и их строки;
- поставщики, если будет добавлена отдельная сущность.

Прямые create/update/delete для складских документов и остатков остаются запрещёнными. Записи выполняет worker через Admin SDK.

## Разделение чтения и записи

### Чтение

Приложение читает данные непосредственно из InstantDB через реактивные queries:

```text
InstantDB → useQuery → UI
```

После изменения статуса в приложении или админке все активные клиенты получают новое состояние автоматически.

Запросы должны быть определены и экспортированы из `@lumo/data`, а не собираться отдельно в каждом приложении.

### Запись

Все изменения проходят через activation worker:

```text
Staff app → staff warehouse endpoint → warehouse command runner → InstantDB transaction
```

Целевой endpoint:

```text
POST /v1/staff/warehouse-commands
Authorization: Bearer <Instant refresh token>
Content-Type: application/json
```

Тело запроса:

```json
{
  "operationId": "stable-uuid-for-this-attempt",
  "venueId": "venue-id",
  "kind": "receive-delivery",
  "payload": {}
}
```

`operationId` создаётся один раз перед отправкой. При сетевом retry повторяется тот же `operationId`. Новый UUID при каждом retry создавать нельзя.

Полноценная offline-очередь не нужна, но retry после потерянного HTTP-ответа всё равно должен быть идемпотентным.

## Модель закупочного листа и приёмки

Нельзя перезаписывать заказанное количество фактическим. Иначе теряется история договорённости с поставщиком.

Минимальная модель строки:

```ts
interface DeliveryLine {
  id: string;
  productId: string;
  name: string;
  unit: string;
  orderedQuantityMilli: number;
  receivedQuantityMilli: number | null;
  orderedPriceTiyin: number | null;
  receivedPriceTiyin: number | null;
}
```

Правила:

- до приёмки `receivedQuantityMilli === null`;
- если позиция не приехала, `receivedQuantityMilli === 0`;
- если количество отличается, сохраняются оба значения;
- незапланированная позиция получает `orderedQuantityMilli === 0`;
- исходная строка закупочного листа не удаляется из-за недопоставки;
- склад пополняется только на `receivedQuantityMilli`;
- сумма фактической поставки считается по фактическому количеству и цене.

Если одна заявка может приезжать несколькими партиями, до реализации необходимо отдельно согласовать частичную приёмку. В таком случае одной пары полей на строке может быть недостаточно: потребуется отдельный receipt на каждую фактическую поставку.

## Команда приёмки

Целевой контракт:

```ts
interface ReceiveDeliveryPayload {
  documentId: string;
  expectedVersion: number;
  lines: Array<{
    lineId?: string;
    productId: string;
    receivedQuantityMilli: number;
    receivedPriceTiyin: number;
  }>;
}
```

Семантика:

- `lineId` присутствует для строки исходного закупочного листа;
- отсутствие `lineId` означает ингредиент, добавленный при приёмке;
- worker повторно читает документ и проверяет venue, status и version;
- worker валидирует продукты, единицы и количества;
- worker одной транзакцией сохраняет фактические строки;
- той же транзакцией создаются `inventoryMovements`;
- той же транзакцией обновляются `stockItems`;
- документ переводится в `received`;
- операция связывается с `actorEmployee`;
- повтор той же операции возвращает сохранённый результат;
- конкурентная операция получает `409 resource_conflict`.

Текущий `receive-delivery` принимает только `documentId` и проводит сохранённые строки. Его необходимо расширить до подключения редактирования фактического количества в staff app и дашборде.

## Разделение интерфейсов

### Приложение сотрудников

Полный рабочий сценарий:

- создать закупочный лист;
- выбрать поставщика и склад;
- добавить, удалить или заменить ингредиенты;
- указать заказанное количество и цену;
- отправить закупочный лист;
- открыть ожидаемую поставку;
- указать фактическое количество;
- добавить незапланированный ингредиент;
- изменить фактическую цену;
- отметить отсутствующую позицию количеством `0`;
- принять поставку;
- увидеть автора, время и результат операции.

### Полная форма админки

Должна поддерживать те же возможности приёмки:

- добавление ингредиентов;
- изменение фактического количества;
- изменение фактической цены;
- фиксация недопоставки;
- проведение поставки.

### Дашборд админки

Только быстрый сценарий:

- «Принять как есть»;
- изменить количество существующих строк;
- указать `0` для отсутствующей позиции;
- увидеть расхождение и новую сумму;
- перейти по ссылке «Открыть полную приёмку».

Дашборд не добавляет ингредиенты и не меняет поставщика, склад или состав исходного документа.

## Обработка одновременной работы

Приложение и админка могут открыть один документ одновременно.

Ожидаемое поведение:

1. Первый пользователь успешно принимает поставку.
2. Вся поставка, строки, движения и остатки фиксируются атомарно.
3. Второй пользователь получает реактивное обновление статуса.
4. Если второй успел отправить старую форму, worker отвечает `409 resource_conflict`.
5. UI показывает, что документ уже изменён или принят, и обновляет данные.

Сообщение пользователю:

```text
Поставка уже была изменена или принята другим сотрудником. Данные обновлены.
```

Нельзя молча перезаписывать новую версию старой формой.

## Почему одной InstantDB-синхронизации недостаточно

InstantDB гарантирует атомарность операций внутри одного `db.transact` и обновляет live queries в реальном времени. Однако обычный клиентский read → update не является документированным compare-and-swap.

В Lumo складские команды выполняются через Admin SDK, который обходит permission rules. Поэтому конкурентная защита остаётся обязанностью command runner. Текущий механизм `operationId + commandOperations + commandClaims + version` нужно сохранить.

Официальная документация:

- [InstantDB: Writing data and atomic transactions](https://instantdb.com/docs/instaml)
- [InstantDB: Permissions, data and newData](https://instantdb.com/docs/permissions)
- [InstantDB: Backend SDK](https://instantdb.com/docs/backend)

## Этапы интеграции

### Backend foundation

1. Добавить связь `$user ↔ employee`.
2. Добавить procurement capability сотрудника.
3. Добавить scoped permission rules для procurement-чтения.
4. Добавить `authorizeStaff` в activation worker.
5. Добавить `/v1/staff/warehouse-commands`.
6. Разрешить команды по procurement-роли.
7. Добавить `actorEmployeeId` в command context.

### Data contract

1. Разделить заказанные и фактически принятые значения.
2. Расширить shared типы в `@lumo/data`.
3. Экспортировать запросы закупочных листов и ожидающих поставок.
4. Расширить `receive-delivery` фактическими строками.
5. Добавить серверную валидацию незапланированных строк.
6. Если нужна частичная приёмка, согласовать отдельную модель receipts до реализации UI.

### Staff app

1. Перенести или создать приложение в `apps/staff`.
2. Подключить `@lumo/data` через `workspace:*`.
3. Подключить тот же InstantDB app ID.
4. Реализовать magic-code auth.
5. Получать employee и venue из authenticated identity.
6. Использовать shared queries для чтения.
7. Использовать staff command client для записи.
8. Обрабатывать `409`, `401`, `403` и retryable сетевые ошибки.

### Admin and dashboard

1. Перевести полную приёмку на новый payload фактических строк.
2. Использовать ту же команду, что staff app.
3. Добавить quick-receive drawer на дашборде.
4. Не дублировать проведение поставки в React-компонентах.

## Definition of done

Интеграция завершена, когда:

- staff app и admin читают одни документы из InstantDB;
- сотрудник входит под персональным Instant-пользователем;
- worker однозначно определяет `employee` и venue;
- прямые складские записи с клиента запрещены;
- сотрудник с разрешением может создать и принять поставку;
- полная приёмка позволяет добавить ингредиент;
- дашборд позволяет только изменить количество существующих строк;
- заказанные значения сохраняются после приёмки;
- склад обновляется по фактически принятым значениям;
- повторный HTTP-запрос не проводит поставку дважды;
- одновременная приёмка из app и admin приводит к одному успеху и одному `409`;
- автор и источник приёмки видны в аудите;
- после приёмки все открытые клиенты получают новый статус без ручного refresh.
