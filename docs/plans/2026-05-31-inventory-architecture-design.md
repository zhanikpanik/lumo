# Inventory Architecture — Non-blocking Advisory Model

**Date:** 2026-05-31
**Goal:** Склад никогда не блокирует работу официанта. POS = advisory only.
**Status:** Validated
**Session:** Brainstorm skill

---

## Context

**Problem:** Сейчас при списании ингредиента модалка `DeadLetterModal` вылезает поверх всего интерфейса и блокирует официанта. В час пик это парализует работу.

**Корневая причина:** POS слепо верит Supabase и синхронно ждёт ответа склада. Если Supabase ≠ реальный склад (а так всегда), ошибки сыплются на официанта.

**Target:** Приложение не опозорится в первый час в реальном ресторане.

---

## System Map

### Players & Incentives

| Игрок | Приложение | Что хочет |
|-------|-----------|----------|
| Официант | POS | Быстро создать заказ, не думать о системе, не ждать |
| Кассир | POS | Принять оплату без ошибок, закрыть смену с точной выручкой |
| Повар/Бармен | PWA | Видеть заказы, знать что готовить, видеть остатки |
| Управляющий | Admin/PWA | Выручка, склад, контроль персонала |
| Разработчик | — | Стабильность, расширяемость |

### Stocks & Flows

| Stock | Flow |
|-------|------|
| Заказы | NEW → COOKING → READY → PAID → CLOSED |
| Склад | Приход → Резерв? → **Списание (только при CLOSED)** |
| Dead Letter Queue | Фейлы → Retry 5s/15s/45s → Успех или Alert в админку |
| Нотификации | События → Bell (официант) / Admin alerts (управляющий) |

### Key Insight

**Списание происходит один раз — при закрытии/оплате чека.** Не при создании заказа. Это означает:

- До оплаты: нет списания → нечего откатывать при отмене
- После оплаты: блюдо приготовлено → списание необратимо
- Единственный edge case (оплатили, передумали → refund): возврат денег, склад не трогаем

## Design Decisions

### 1. Склад = Advisory, Not Controlling

- **Read path:** остатки показываются как предупреждения, НЕ блокируют заказы
- **Write path:** списание — fire-and-forget, через retry-очередь
- Официант видит информацию (что заканчивается), но не технические ошибки

### 2. Поток списания

```
Официант создал заказ → Заказ NEW
   ↓
Повар готовит (без списаний)
   ↓
Официант оплачивает / закрывает чек → Заказ CLOSED
   ↓
Списание → deadLetterStore.enqueue() → retry 5s/15s/45s → Supabase
   ↓                              ↓
Заказ закрыт (UI)             3 retry exhausted → alert в админку/PWA
```

### 3. Разделение видимости

| Событие | Официант (POS) | Управляющий (Admin/PWA) |
|---------|:---:|:---:|
| Ингредиент < 20% | 🔔 Bell + бейдж | 🔔 Alert |
| Ингредиент = 0 | 🚫 Блюдо затемнено | 🔔 Alert |
| Списание упало (retry 1-3) | ❌ Ничего | ❌ Ничего |
| Списание упало (exhausted) | ❌ Ничего | 🔴 Alert |
| Склад офлайн | ❌ Ничего | 🔴 Alert |
| Заказ готов (от кухни) | 🔔 Bell | — |
| Коллега просит помощи | 🔔 Bell | — |

**Принцип:** POS изолирован от инфраструктурных проблем. Показывает только то, что помогает обслуживать гостя.

### Edge Cases

| Сценарий | Решение |
|----------|---------|
| Заказ отменён ДО оплаты | Списывать нечего, просто меняем статус |
| Заказ оплачен, списание в retry | `deadLetterStore` дожмёт. Заказ уже closed. |
| Retry queue 50+ после долгого офлайна | Пачками по 10, не спамить Supabase |
| Два официанта заказали последнюю порцию | Не блокировать; блюдо затемнится при следующем fetch'е |
| Официант удалил блюдо из незакрытого заказа | Списывать нечего |

## 2nd & 3rd Order Effects

- **1st-order:** Официант больше не видит модалку склада
- **2nd-order:** Поток UI быстрее → меньше стресса → меньше ошибок
- **3rd-order:** `deadLetterStore` становится универсальным слоем для всех async-операций: склад, E-Kassa, синхронизация
